# 录制并诊断一次测试

[指南目录](README.md) · [English](../en/recording.md) · [日本語](../ja/recording.md)

录像用于观察玩家看到的画面，组件 CPU 记录用于查找卡顿区间有哪些调用。两者不能互相替代。

## 采集一次场景变化

1. 启动游戏测试，从工具菜单打开游戏运行资料采集设置。
2. 选择保存目录和能区分测试的标签，例如 `Menu-Arena-return`。需要对照时同时启用视频与 CPU 采样。
3. 录视频时选择可运行的 `ffmpeg.exe`。引擎中的媒体解码 DLL 不是 FFmpeg 命令行程序；只采 CPU 不需要 FFmpeg。
4. 按需选择游戏音频、输入字幕与鼠标。系统指针只在游戏目标窗口活动，且指针位于未被遮挡的客户区内时叠加，不是桌面录屏。
5. 开始采集，执行转场，结束并保存。等待状态成为 `Completed` 再把 MP4 视作最终文件；仅关闭设置窗口不会停止采集。

录制器等待首个真实游戏帧，默认最长 120 秒；等待期间不生成黑帧，也不消耗视频时长预算。没有绑定游戏输出上下文之前，不能录下 Windows 建窗和编译过程。失败状态仍然是失败，`gameplay.partial.mp4` 可能提供仅视频的恢复片段，不代表完整音视频。

[CaptureExample API 示例](../examples/CaptureExample.cs)把启动任务返回给调用方。调用方应处理结果与异常，不在游戏回调中使用 `.Wait()` 或 `.Result`。`Stop` 不阻塞，封装期间查询 `SYSTEM_Game_Recording.Status`。FFmpeg 可通过配置、`SOUSEI_FFMPEG` 或 PATH 查找。

## 在查看器中打开资料

测试结束后在游戏运行资料库双击记录，或者单独运行 **Sousei.EvidenceViewer.exe**，拖入资料目录或 ZIP。保留运行索引、视频、CPU 会话索引与对应 `.profile` 目录；只移动 `.trace-session.json` 会丢掉其压缩分段。

使用共同时间基准对齐视频与 CPU。如果查看器提示无法对齐，不要仅凭时间数字相近判断它们对应；有外部参照时才手动指定偏移。

画面卡住时，选择播放时间继续前进、但画面没有变化的区间。展开引擎或用户组件轨道，查看调用与未返回跨度，再确认这些调用在等待什么。应检查当前录像区间，而不只检查被重复使用的旧图像采集时刻：逻辑继续运行时，视频也可能重复旧画面。

## 理解数据

| 字段或显示 | 含义 |
| --- | --- |
| 线程编号 | 执行工作的轨道，不是游戏中的组件数量。 |
| 调用次数 | 所选区间内被保留的已插桩调用。 |
| 经过时间 | 包括等待的墙钟跨度；重叠和嵌套跨度不能相加当作 CPU 百分比。 |
| `profiler.stop` 的 `events`、`dropped` | 为兼容保留的有界预览数量与预览淘汰数。 |
| `archiveEvents`、`archiveDroppedEvents`、`archivePath` | 完整档案的数量与位置，判断采集缺失前先检查它们。 |

空轨道可能意味着没开启采集、记录丢失、区间不在覆盖范围，或没有保留下该区间的已插桩调用，不证明组件没有运行。查看器用于 CPU 诊断，不是 GPU 时间或显存分析器。

独立工作线程不能消除采集本身的开销。比较性能时固定采集设置、资源与测试操作，观察多次运行，不以单个最快帧作结论。
